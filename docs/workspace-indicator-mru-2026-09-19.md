# 顶部工作区指示器与 MRU 排序问题

日期：2026-09-19

## 问题现象

使用 Win+数字切换工作区时，实际窗口已经切换到了目标工作区。例如按下 Win+2 后，当前窗口确实出现在第二个工作区；但是顶部 bar 的工作区指示器仍然显示第 1 个位置被选中，或者短暂显示正确位置后又回到第 1 个位置。

这说明问题不在窗口切换本身，而在顶部指示器对“当前工作区”的判断上。

## 两种容易混淆的编号

插件同时处理两种不同含义的编号：

1. **Hyprland 工作区 ID**：由 Hyprland 管理的实际工作区，例如 1、2、3。这是当前焦点的真实来源。
2. **顶部 bar 的视觉槽位**：根据插件的显示顺序渲染出来的第 1、2、3 个按钮。启用 legacy/MRU 排序后，这个顺序会随着最近使用记录变化。

MRU（Most Recently Used）排序会把最近访问的工作区移动到列表前面。因此，某个工作区的实际 ID 不一定等于它当前在顶部列表中的下标：实际 ID 为 2 的工作区可能显示在第 1 个视觉槽位，反过来也可能成立。

所以不能用“MRU 列表的第几个元素”推断当前焦点，也不能把视觉槽位数字当成 Hyprland 工作区 ID。

## 根因判断

顶部 widget 原本直接使用 `Hyprland.focusedWorkspace?.id` 判断按钮是否聚焦。后来为了让 bar 在焦点变化后刷新，增加了一个共享的 `focusedWorkspaceId`，但它优先读取 `Local.HyprlandData.activeWorkspace?.id`：

```qml
Local.HyprlandData.activeWorkspace?.id
    ?? Hyprland.focusedWorkspace?.id
```

这个派生属性可能在刷新时机不一致时保留旧值。由于它位于 `??` 的前面，只要旧对象仍然存在，就不会再读取后面的实时焦点值，最终表现为指示器固定指向工作区 1。这个值源还容易与 MRU 列表刷新混淆，让问题看起来像是切换逻辑把工作区改回去了。

此前为排查“跳回 1”临时加入过工作区槽位去重、自动提升 MRU 和日志输出。这些改动会影响切换流程，不能作为顶部指示器问题的修复方案，因此应当移除。

## 修复边界

本次只修复顶部 bar 指示器：

- 指示器直接以 `Hyprland.focusedWorkspace?.id` 作为当前焦点工作区。
- 使用插件已有的数据刷新序号，确保焦点变化后重新计算绑定。
- MRU/legacy 的显示顺序保持不变。
- Win+数字的槽位解析、Hyprland 切换 dispatch、工作区路由保持不变。
- 不修改 `shell.json` 中的 `sortMode`，也不引入其他插件或接口层的行为变化。

修复后的判断关系是：先由 MRU 模型决定按钮的显示顺序，再用每个按钮携带的真实工作区 ID 与 Hyprland 当前焦点 ID 比较。按钮的文字也始终显示真实工作区 ID，而不是显示数组下标；当前工作区不再被替换成无法辨认编号的图标。这样即使 MRU 把工作区 2 排到第一个视觉位置，顶部仍然显示 `2`，不会被误认为工作区 1。

## 验证标准

1. 按 Win+2 后，窗口仍按原逻辑切换到目标工作区。
2. 顶部指示器高亮对应当前真实工作区，而不是固定高亮第 1 个按钮。
3. 连续在多个工作区之间切换时，MRU 顺序可以变化，但高亮不会因为列表重排而回到 1。
4. 不出现重复 dispatch，也不改变原有工作区槽位路由。

## 最终产品方案

MRU 与固定数字无法同时表达同一种编号含义，因此设置面板提供一个明确的
`MRU workspace ordering` 开关：

- 关闭时，Overview 和顶部 bar 都按固定的真实工作区 ID 排列，顶部显示
  `1 2 3 4 5`，Win+数字保持固定工作区语义。
- 开启时，Overview 和 Win+数字按最近使用顺序工作；顶部隐藏数字，显示
  `WORKSPACE`，避免把会变化的 MRU 槽位误认为固定工作区编号。

两种模式切换时，快捷键、Overview 顺序和顶部显示一起切换，不保留混合状态。
